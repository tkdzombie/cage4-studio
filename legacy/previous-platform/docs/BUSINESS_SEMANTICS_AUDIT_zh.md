# 业务安全要求的模拟能力核验

日期：2026-10-21。锁定模拟器：`8c3c50ca54b176c2de199847944e8dcc035497e3`。这是机制与测量语义核验，不是新的策略性能验证。

## 结论与要求调整

1. **OT 服务状态与 Green 业务结果必须分开。** 若主张关键 OT 服务连续性，必须直接识别相关服务的运行与可靠性状态，不能用 GreenLocalWork 成功率替代。
2. **当前 GreenAccessService 不能证明目标服务健康。** 锁定源码的服务健康谓词没有被调用。它仍能反映显式网段阻断造成的访问失败，但不能承载完整的服务可用性 SLA。
3. 主要求继续是当前使命关键业务连续性，但细化为“关键服务状态”和“实际业务完成结果”两个可区分的证据层。前者的保护清单须明确，后者是业务侧验证，不将两者混成同一个安全事件。
4. 任务隔离属于运行规则，不单独充当安全 MARL 难度来源；当前锁定实现中的任务通信政策与实际防火墙阻断状态也必须区分。
5. 保持现有官方模拟器和旧实验原样。修正官方服务检查会改变环境转移/奖励结果及随机数使用，必须作为新的模拟器变体，不属于无影响的小修复。

## 新增证据及成本

两个最小构造探针，不执行环境回合；另对此前已预选的训练回合1900按原种子与动作重演499步。499步官方回报逐步全部等于原回放，没有更新权重，没有访问最终评估场景。

新增模拟器 transition 为499，新增训练回合为0。本次与此前“零交互”的快速适用性审计不同，应分别计量。

私有摘要：实验control中的 `business-semantics-probe.json`，包含源文件SHA、探针、分阶段业务计数和源/目的区域访问计数。不上传原始实验数据。

## 发现一：跨主机访问绕过服务健康检查

锁定 `GreenAccessService.execute()` 使用：

```python
if not self.available_dest_service:
    return obs
```

这里检查的是绑定方法对象，没有执行 `available_dest_service(state)`，因此没有触发其中的服务活动性或可靠性判断。

最小探针固定目的主机、构造空服务列表，并给实例的健康谓词一个计数且始终返回False的函数。结果：健康谓词调用次数0，未阻断访问返回成功；增加显式网段阻断后返回失败。探针隔离的是谓词调用行为，**不是实际环境中所有业务失败的概率**。

此外，该谓词非OT分支存在对未在方法中定义的 `session` 的引用。它当前被未调用问题遮蔽；不能仅补一对调用括号便宣称服务访问逻辑已修好。完整修复应另行设计并验证。

因此，当前“Access成功”应解释为该模拟动作按现有逻辑成功，不可写成目标应用/OT服务健康或完成真实业务事务。

## 发现二：本地工作不专门检验OT

`GreenLocalWork.execute()` 从本机活动服务列表随机选择一个服务，再按它的可靠性决定结果。作战区主机同时具有SSHD及OT等服务；OT停止但其他服务仍运行时，本地工作可能成功。

最小构造：OT不活动，SSHD活动且可靠性100，结果LocalWork成功。此构造与源码选择机制一致，不是额外故障注入到正式实验。

原回合重演也观察到：当前任务区有16次本地工作机会发生在本机OT不活动时，其中10次成功。统计为本回合的动作机会数，不能当成总体发生率或独立样本推断。

| 任务阶段的对应作战区 | LocalWork尝试/失败 | Access尝试/失败 | OT不活动时LocalWork尝试/成功 |
|---|---:|---:|---:|
| Mission A：A区 | 205 / 6 | 244 / 0 | 14 / 8 |
| Mission B：B区 | 583 / 13 | 522 / 0 | 2 / 2 |

这使得“本地工作成功”作为一般本地业务结果仍有意义，却不适合作为严格OT连续性的替代测量。

## 发现三：服务状态可以逐步测量，但业务关键性仍须定义

锁定场景在作战区主机部署OT服务；Impact可以停止OT服务，DegradeServices会降低服务可靠性，Restore恢复主机原始服务。研究者可以逐步记录服务状态，不必依赖随机业务请求是否恰好发生。

同一重演回合的当前任务区状态采样：

| 阶段 | 官方回放step编号 | OT主机×步骤样本数 | OT不活动样本数 | 可靠性低于100样本数 |
|---|---|---:|---:|---:|
| Mission A | 168–334 | 835 | 45 | 63 |
| Mission B | 335–499 | 2475 | 205 | 303 |

不活动与可靠性降低是不同字段，不能相加当成互斥事件。表中按所有拥有OT服务的区域主机计数；不冒称所有这些主机均已由业务所有者确认关键。

可行的下一步测量结构（尚非cost定义）：

- 对每个明确列入保护清单的OT主机，逐步记录阶段、服务是否存在/活动、可靠性值及采样时刻。
- 分别报告每主机失活采样数、最大连续失活采样数，以及任务区中的受影响主机数，不先做全网平均。
- 单独报告Green机会数、业务类型、源/目的区域和结果；无请求期标为“没有业务机会”，不是业务成功。
- 状态快照中的连续失活采样不等于现实分钟或精确连续时间停机；缺失快照也不能补为正常。

研究者服务状态不会直接成为actor输入。若后续将某个状态指标定义为训练cost，也应只按预注册协议提供成本信号；不能把真实感染、全局服务状态或Green详细事件加入actor。

## 发现四：通信政策与实际阻断不能混写

阶段切换时，`SimulationController._update_agents_allowed_subnets()`更新的是Green的允许访问区域信息。`State.blocks`由防火墙动作维护。仅依据官方使命图中的0/1，不能直接断言当前实际防火墙配置已经执行了同样的策略。

后续若研究隔离合规，须明确评价的是批准的通信政策、Blue实际规则变化，还是实际越界通信；还须核验这些信息进入执行策略的合法路径。当前编码器未显式传入完整政策和防火墙状态。保持BR-03为设计边界，不将尚未验证的政策执行语义当成现成约束。

## 对任务选择的影响

优先保留：**当前使命关键OT服务的运行连续性**，附带业务机会结果作为外部验证。其潜在测量对象是真实服务状态，不再仅将官方Green损失重新归一化。

仍然缺少：保护服务清单的业务依据、不可接受退化/中断的界限、风险容忍度，以及这一要求是否实质改变防御策略选择的证据。对攻击损失施加约束仍可能与reward高度同向，直接改用OT状态并不会自动解决任务辨识力问题。

暂不采用：GreenAccessService成功率作为服务健康保证、Restore次数上限作为误伤保证、未经业务来源确定的恢复时间预算、只靠政策动作屏蔽构成的安全MARL主任务。

因此目前仍不启动主论文实验。先补齐测量与业务参数，再判断是建立独立命名的CAGE4安全变体，还是仅把它保留为探索性应用。

## 可复现的最小探针

在安装锁定模拟器的Python中运行：

```bash
python ops/probe_business_semantics.py
```

可加 `--output <新的私人JSON路径>` 保存结果，拒绝覆盖已有文件。该脚本不连接服务器，不读取训练权重，不改官方源码，不执行环境回合。它记录实际行为和源文件SHA；换版本后输出可能改变，不应为了让历史探针输出保持一致而保留缺陷。
